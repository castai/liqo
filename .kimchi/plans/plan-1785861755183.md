## Goal
Add a `Replicas` field to `GatewayClient` and `GatewayServer` CRDs so that the gateway controllers create N independent deployments (one replica each), each pod receiving a stable `--replica-id` argument that persists across restarts.

## Constraints
- No new external dependencies.
- Backward-compatible: default `Replicas` is 1; existing single-replica behavior unchanged.
- Existing public APIs are preserved; new status fields are additive only.
- Use existing patterns in the repository (controller-runtime, dynamic templates, `make generate`).
- CRDs are regenerated with `make generate`.

## Verification Strategy
- **Unit/Envtest:** New controller tests verify the number of deployments/services, argument injection, and status aggregation.
- **Build:** `go build ./...` succeeds.
- **Generation:** `make generate` produces clean diffs only for the new fields.
- **Helm:** `helm template deployments/liqo ...` renders the new fields.
- **Lint/Test:** `make test` passes (or the repository's standard test command).
- **Manual:** Deploy a `GatewayServer`/`GatewayClient` with `replicas: 3` and verify three one-replica deployments, three server services, and `--replica-id` args.

## Decision Log
1. **Per-replica identifier passed as argument:** Added `--replica-id` flag (default `"0"`) while keeping `--name` equal to the parent gateway name, matching the user's choice.
2. **Shared vs. per-replica secret:** Share the same WireGuard secret across replicas, as chosen by the user. Secret name remains based on the parent gateway.
3. **One service per server replica:** Implement a service per replica, each selecting its own replica label, and report all endpoints in status.
4. **Per-replica Connection and status names:** Internally derive `Connection`/route/firewall pod names as `<parent-name>-<replica-id>` so active replicas do not overwrite each other's status, while the user-visible `--name` stays unchanged.
5. **Backward compatibility:** Keep `Status.Endpoint` and `Status.InternalEndpoint` populated with the first endpoint so existing consumers continue to work while migrating to the new list fields.

## Risks
1. **Active/active WireGuard behavior:** Multiple pods sharing the same private key but exposing different endpoints is unusual for WireGuard peer configs. Remote clients/servers must be able to handle multiple endpoints for the same public key. Likelihood: medium. Mitigation: document the behavior and consider future work to generate per-replica keys if needed.
2. **Connection status conflicts:** Without per-replica `Connection` names, all replicas would update the same status. Mitigation: derive per-replica `Connection` names as decided.
3. **Status aggregation on scale-down:** The controller must reliably clean up `Status.Endpoints`/`InternalEndpoints` entries for removed replicas. Mitigation: recompute the lists from observed deployments/services on every reconcile.
4. **Helm template default values:** Existing `values.yaml` `networking.gatewayTemplates.replicas` now controls the default number of deployments rather than Deployment replicas. Mitigation: update comments in `values.yaml` and ensure the default remains 1.
